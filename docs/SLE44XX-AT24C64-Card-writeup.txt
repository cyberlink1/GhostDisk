===============================================================================
SLE4442 Smartcard Integration Concept
(AT24C64 / SLE4428 Compatibility Intent)
===============================================================================

This document describes the intended design for integrating low-cost memory-
type smartcards (AT24C64, SLE4442, SLE4428) into a cryptographic authentication
workflow. These cards are NOT true microcontroller smartcards — they are
EPROM-style storage devices with optional PIN protection. However, they are
inexpensive, readily available, and can be leveraged as secure key containers
paired with host-side cryptographic enforcement.

The original goal was to support these legacy cards through the ACS ACR39U
reader. While ACR39U can fully interface with SLE-series cards, there is NO
existing middleware, making custom development necessary. AT24C64 cards further
complicate this by requiring an external I2C interface — often the same cost as
the ACR39U itself.

I have experience writing C for microcontrollers but do not currently feel
confident enough to implement the full provisioning stack and PC/SC middleware.
Therefore, this README serves as a design reference and invitation for
collaboration. Any developers willing to help build the required utilities are
welcome.

===============================================================================
Concept Overview
===============================================================================

Although these cards lack onboard crypto, the idea is to store symmetric-
encrypted private keys and enforce:

  - Host-side cryptography (Ed25519, AES-256 / ChaCha20, HMAC-SHA256)
  - Host-side PIN verification
  - Integrity validation using a stored HMAC
  - Anti-replay protection using a monotonic counter

Security is NOT comparable to true secure-element smartcards (e.g., JCOP4),
but may be appropriate for education, hobby projects, and low-risk
authentication systems.

===============================================================================
Card Memory Layout — SLE4442 (256 bytes)
===============================================================================

Offset      Field            Size  Description
----------  ---------------  ----  ----------------------------------------
0x00–0x03  Counter           4B    Monotonic, big-endian
0x04–0x07  Metadata          4B    Version, flags, algorithm ID, salt index
0x08–0x27  HMAC             32B    HMAC-SHA256(counter || encrypted_key)
0x28–0x49  Encrypted Key    36B    Symmetric-encrypted Ed25519 key
0x4A–0xFF  Reserved         182B   Future expansion

All crypto operations occur on the host.

===============================================================================
PIN Handling & Derivation
===============================================================================

PIN is NOT stored in plaintext. Instead:

  Input: User PIN string (alphanumeric)
  KDF: PBKDF2-HMAC-SHA256 (host-side)
  Iterations: 1000
  Salt: Stored in metadata
  Output: 32-byte key → first 3 bytes truncated for SLE4442 PIN format

Used for:
  - Card write protection
  - Key unlock authorization

===============================================================================
Counter Enforcement
===============================================================================

  - 4-byte unsigned big-endian value
  - Incremented only host-side
  - Written per-byte after successful PIN verification
  - On read: verify monotonic increase
  - Provides replay/rollback protection

===============================================================================
Key Encryption
===============================================================================

  - Ed25519 private key → 36-byte compact representation
  - Encrypted using host crypto library (AES-256 or ChaCha20)
  - Stored only after HMAC + PIN validation

===============================================================================
HMAC Integrity Protection
===============================================================================

  - HMAC-SHA256 calculated over:
        counter || encrypted_key
  - Stored at 0x08–0x27
  - Recomputed on read → must match before key usage

Purpose:
  - Detect tampering
  - Prevent unauthorized cloning

===============================================================================
Key Retrieval Workflow
===============================================================================

1. Read counter, encrypted key, and HMAC
2. Recompute HMAC host-side → verify match
3. Derive key-unlock crypto key from PIN
4. Decrypt stored Ed25519 key
5. Validate counter policy → allow usage

===============================================================================
Required Host-Side Components
===============================================================================

  - C PC/SC middleware for SLE4442 card access
  - C cryptographic library (OpenSSL, libsodium, or equivalent)
  - Provisioning tool for initial setup
  - Authentication agent for usage/read flows

===============================================================================
Security Disclaimer
===============================================================================

This design assumes that attackers MAY physically extract or clone card memory
and MAY tamper with a compromised host runtime. Protection is based on
cryptographic secrecy rather than card hardware security.

- Private keys are always stored encrypted
- PIN-derived key material is never written to the card
- HMAC and a monotonic counter prevent rollback or tampering
- Offline brute-force is limited by PBKDF2 cost and counter checks

Physical access to the card alone, or a full EEPROM dump, does NOT reveal key
material or allow unauthorized signing operations.
